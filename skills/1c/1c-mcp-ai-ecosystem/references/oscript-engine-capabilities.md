# Oscript 2.1.0: проверенные возможности движка + формат .epf + REST toolkit (2026-08-11)

Всё проверено на живом движке `C:\hermes\tools\engine\oscript-2.1.0` (скрипты .os, вывод консоли — **cp866**; читать через `oscript script.os > out.txt; iconv -f cp866 -t utf-8 out.txt`).

## Что есть в ядре oscript 2.1.0 (конструкторы/функции — ЕСТЬ)

| Объект/функция | Статус |
|---|---|
| `ЧтениеXML` / `ЗаписьXML` / `ЧтениеJSON` / `ЗаписьJSON` | ✅ есть — основа статического контура |
| `ПотокВПамяти` / `ЧтениеТекста` / `ЗаписьТекста` / `СтрНайти` / `Выполнить` | ✅ есть |
| `COMОбъект` (`Новый COMОбъект("V83.ComConnector")`) | ⚠️ механизм есть, НО на машине без зарегистрированной COM-компоненты платформы — `REGDB_E_CLASSNOTREG (0x80040154)`. COM-канал работает только там, где установлена 1С с COM-сервером |
| `ЗапуститьПриложение` | ✅ (процедура, не функция) |

## Чего НЕТ в ядре (проверено — конструктор не найден)

- `HTTPСоединение` / `HTTPЗапрос` / `HTTPОтвет` — **HTTP-клиент в ядре отсутствует!** Только через сторонние пакеты oscript-library (например `1c-http` через opm). Значит «HTTP-вызовы toolkit :6003 из autumn» требуют доустановки пакета — это не «из коробки».
- `ДвоичныеДанные` / `ЧтениеДанных` / `ЗаписьДанных` / `DeflateСжатиеДанных` / `ХешФункция` / `FTPСоединение` / `ИнтернетПочтовыйПрофиль` — бинарного разбора в ядре нет.
- `Запрос` / `МенеджерОбъектов` / `XDTO` / `ТабличныйДокумент` / `ЧтениеZip` — платформенные объекты ВК, oscript их **не эмулирует**. oscript — это НЕ рантайм 1С, это интерпретатор BSL-синтаксиса на .NET.

## Каналы доступа oscript → данные 1С (по практичности, уточнено 2026-08-11)

1. **Статика: XML-выгрузка / CFG / EDT-проект** — нативно (`ЧтениеXML`), уже работает в autumn.
2. **XML-сериализация отчётов/обработок**: конфигуратор → «Сохранить как… XML» → oscript читает нативно. ⭐ Практичный путь для внешних отчётов.
3. **SQL в СУБД** — пакет `sql` (System.Data.SqlClient уже в lib движка): только read-only, маппинг таблиц 1С сложен (уровень DaJet, риск).
4. **COM (V83.ComConnector)** — механизм в oscript есть, но нужна зарегистрированная COM-компонента платформы на машине.
5. **HTTP к опубликованной базе / toolkit** — только через пакет `1c-http` (opm), НЕ в ядре.

## Формат .epf/.erf (внешний отчёт/обработка) — проверено на MCP_Toolkit.epf (1.8 МБ)

- ❌ **.epf — это НЕ zip!** Сигнатура файла `FF FF FF 7F` (бинарный контейнер 1С), а не `PK\x03\x04`. `unzip -l` отказывается («End-of-central-directory signature not found»), `strings` не находит XML-тегов — внутри бинарные блоки со сжатием.
- ⚠️ В **ядре** бинарных примитивов нет (`ДвоичныеДанные`/`Deflate` отсутствуют) — но это НЕ «контейнер не разобрать вообще»: есть нативная oscript-компонента `v8unpack` (oscript-library) — `ЧтениеФайла8`/`ФайлФормата8`, методы `Извлечь`/`ИзвлечьВсе` — читает «Формат8» ПРЯМО из oscript (только parse, read-only, создана для gitsync).

Рабочие пути «разобрать внешний отчёт в XML» (обновлено 2026-08-11 — подробно в `references/onec-binary-unpack-pack.md`):
| Путь | Как | Оценка |
|---|---|---|
| 🥇 Конфигуратор 1С: «Файл → Сохранить как… XML» | XML-сериализация отчёта/обработки → oscript читает `ЧтениеXML` → дальше те же `xml_search`/`config_list` | 🟢 тривиально |
| 🥈 `saby-integration/v8unpack` (Python, PyPI) | `pip install v8unpack`; полный цикл unpack+pack cf/cfe/epf/erf без платформы и java; oscript зовёт `ЗапуститьПриложение` | 🟡 (Python 3.11 уже есть) |
| 🥉 oscript-компонента `v8unpack` | `opm install v8unpack`; `Новый ЧтениеФайла8` → `Извлечь` — разборка прямо из oscript, без внешних процессов; сборки нет | 🟡 |
| 🏅 java-утилита `v8unpack` | классика; java на машине нет → не нужна (saby-вариант закрывает то же без java) | — |

## REST API 1c-mcp-toolkit (проверено по локальному клону `C:\hermes\tools\run\1c-mcp-toolkit`) — живой мост :6003

- Toolkit = EPF «Встроенный сервер» внутри открытой 1С (Python-прокси не обязателен) + JSON-over-HTTP.
- Эндпоинты (REST `POST /api/*`, определены в `onec_mcp_toolkit_proxy/rest_api.py`, валидация в `tools.py`):
  - `POST /api/execute_query` — тело `{query: str, params?: dict, limit: int (1..1000), include_schema?: bool}` → выполнение запроса 1С.
  - `POST /api/get_metadata`, `/api/get_event_log`, `/api/get_access_rights`, `/api/find_references_to_object`, `/api/get_object_by_link`, `/api/get_link_of_object`, `/api/get_bsl_syntax_help`, `/api/execute_code`, `/api/get_screenshot`, `/api/close_session`, `/api/restart_session`.
  - Каналы: `?channel=default` (ChannelRegistry, невалидный → default).
- **Следствие для связки autumn+toolkit**: oscript НЕ пишет COM/OData/BSL-сервисы — «живые» аналитические инструменты = oscript-обёртки над REST toolkit'а (`POST /api/execute_query` + сериализация). BSL-разработка для аналитики не нужна: тексты запросов — это параметр `query`, не код в 1С.

## Архитектурная рамка оценки MCP-кандидатов (2026-08-11, уточнение после правки владельца)

Владелец поправил рамку: «у нас есть рантайм, совмещаем 1c-toolkit с autumn-mcp» — оценивать кандидатов надо в связке:

```
LLM-клиент ←MCP→ autumn-mcp (oscript: фасад, статика, оркестрация)
                      │ HTTP JSON
                      ▼
              1c-mcp-toolkit :6003 (EPF в открытой 1С, REST /api/*)
                      │ BSL
                      ▼
                    База 1С (рантайм)
```

Правило пересчёта: кандидат «выполнить запрос/прочитать метаданные/журнал/права» = обёртка над уже существующим эндпоинтом toolkit + текст запроса → 🟢-🟡 (дни), а не 🟡-🔴 (как казалось без связки). «Тяжёлое» (парсер 1CD, DaJet-SQL, embeddings/Neo4j, собственный BSL-парсер) отпадает: рантайм уже решает эти задачи. Полный пересчёт 18 решений — в `~/guides/09-1c-mcp-analyst-oscript.md` (разделы 2а, 3, 5).

Питфолл оценки: не путать «oscript умеет COM» с «COM работает на этой машине» — механизм в ядре есть, но регистрация компоненты — отдельное условие окружения.
