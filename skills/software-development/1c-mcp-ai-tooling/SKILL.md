# 1С MCP / AI tooling discovery and integration

Collect, classify, and integrate MCP-серверы и ИИ-инструменты экосистемы 1С (Model Context Protocol, Skills/агенты для Claude Code/Cursor/Codex, LLM-интеграции, RAG, бенчмарки). Пользователь работает с 1С-проектом (dev-базы, файловая+серверная), уже интегрирован мост `1c-mcp-toolkit` (ROCTUP, прокси :6003).

## Trigger
- «найди/отбери MCP или ИИ-инструменты для 1С», «изучи каталог X, отбери по теме Y», «собери список возможностей и классифицируй».
- Обновление/пересборка каталога OpenYellow.
- Выбор стека MCP-инструментов под задачу (контекст платформы, данные ИБ, RAG по коду, Напарник).

## Primary source: OpenYellow catalog
`https://openyellow.org` — агрегатор open-source проектов для 1С. **Сайт — статический SPA, данных в HTML нет.** Весь контент отдаёт JSON API:
- Base: `https://openyellow.openintegrations.dev/api`
- `GET /api/repos?filter=top&pageSize=100&page=N` — карточки репозиториев; **pageSize режется до 100** (запрос 4000 вернул 100) → пагинация обязательна; полный каталог ~3600 репо = 36 страниц.
- Поля карточки: `id, name, url, author, stars, forks, license, isFork, description, tags, ai_summary, updated, createddate` (проверять `.get()`).

Скрипт полного фетча: `scripts/fetch_openyellow.py` (пишет `oy_all_repos.json`). Подробности API, категории, пифоллы — `references/openyellow-catalog.md`.

## Workflow

1. **Скрейп API, не HTML.** Если сайт SPA — вытащить эндпоинт из `js/config.js` / `js/main.js` (curl, не браузер). Пагинация по 100, консьолид в один JSON.
2. **Отбор/классификация строго по `name` + `description` + `tags`** (lowercase, regex с word boundaries). `ai_summary` — НИКОГДА не источник совпадений: субстроки («агент» в чужих смыслах, «бот» внутри «работа», «инструкции») дают ложные срабатывания; поле полезно только как готовое описание «возможности» в выдаче.
3. **Дедуп форков** по `name.lower()`: предпочитать `isFork == 0` (и/или максимум звёзд); замечать, когда один репо форкают многие (в OpenYellow таких десятки).
4. **Ручная курация по именному списку** (см. `references/openyellow-catalog.md` → «Что вырезать»): EDT/VSCode-плагины, парсеры ТЖ/логов без AI, CI-пайплайны, драйверы сканеров ШК, подсветки синтаксиса. Имена вырезать EXACT lowercase (подчёркивания vs дефисы — частая ошибка).
5. **Формат выдачи пользователю**: Markdown-каталог (секции × таблицы «репо | автор | ⭐ | обновлён | лицензия | возможности») + CSV (`;`-разделитель, utf-8-sig) рядом. Сначала показать сводную таблицу «категория × что даёт × кол-во», потом детали.
6. **Интеграция**: связать найденное с уже работающим стеком пользователя (см. `references/openyellow-catalog.md`, раздел «Рекомендуемый стек»).

## Pitfalls

- `web_extract`/browser на SPA-каталогах часто пустой — сразу к API.
- `curl -o /tmp/...` в git-bash на Windows падает с exit 23 → писать в `$HOME`.
- Heredoc-скрипты с длинным Python дают синтакс-ошибки — писать скрипт через `write_file`, потом `python file.py`.
- Категория «шаблон/стандарт» охватывает и генераторы, и ревьюеры — проверять по описанию.
- `ai_summary`-аннотации автогенерённые («парсер», «MCP») — не верить именам, верить описанию.
- **После write_file/patch с длинной кириллицей** — проверять на артефакты: CJK-иероглифы вместо кириллицы (было 2026-08: «Нап喏» вместо «Напарник», «ВаXUnit» вместо «YaXUnit»; скан-проверка: python по диапазонам `\u4e00-\u9fff` и `[A-Za-z]+[\xd0-\xd1][\x80-\xff]`) и лишние `\"` в коде-фрагментах (двойные кавычки внутри backtick превращаются в `-`; в кодовых примерах предпочитать одинарные: `pip install '.[http]'`). Грепать после каждого мультиханча.

## Документация решений («подробно как в прошлый раз», формат владельца)

- Решения фиксируются в `~/guides/`: 00 — сводный (паспорт портов, конфликты, этапы, вопросы владельцу), 01–03 — тематические, 04 — инвентарь карточками всех инструментов, 05 — BSL-анализаторы, 06 — план развёртки. Новые solutionLine дописывать в `references/ecosystem-decisions.md` и синхронизировать 00/04/(06).
- **Формат карточки инструмента** (владелец требует полные карточки, не краткое сравнение): «Что это / Выполняемые задачи / Транспорт / Зависимости / Интеграция (2 клиента: Hermes, Cursor) / Роль в стеке».
- Режим работы: **анализ → гайд → руками**. Во время планирования ничего не устанавливать и не запускать; гейт каждого этапа — явное «ГО» владельца («не торопись», «сделай гайд» — сказано дважды).
- Новый инструмент оценивать по: README (curl raw, обе ветки main/master), дубли с уже выбранным (таблица «основной | резерв/музей»), влияние на Java/порты/зависимости, позиция по слою (0 живой мост, 1 статика, 1.5 LLM-ядро/Напарник, 2 справка, 2а анализаторы, 3 навыки, 4 запасы).
- **Дублёр уже закрытой функции = вычеркнуть + симптом-гейт**: `bsl-context` (сверка LLM-кода с API платформы) исключён — эту проверку уже дают справка (`syntax_help_search`) и Напарник (`search_1c_documentation`); возвращать только по симптом-гейту (агенты систематически выдумывают API).
- **Критерий «основной» для Hermes — CLI-канал, а не LSP**: Hermes — агент/чат, не редактор, «подсветка» там неприменима. Анализатор выбирать по headless-отчёту (CLI `analyze --reporter json|sarif` → LLM читает в диалоге, правит, повторяет), а не по LSP/автодополнению (это только под будущие IDE). Потому основной — bslc (Docker, CLI по запросу), а bsl-analyzer (Rust, силён в LSP/MCP) — опция.
- **Владелец может перевернуть выбор «основной/резерв» одним фокус-сообщением** («нене, рано убрал... хочу bslс» 2026-08-09). При реверсе обновлять СРАЗУ все артефакты: 06 (план/этапы/таблицы), 04 (карточки), 00 (паспорт/конфликты/дубли/вопросы), `references/ecosystem-decisions.md` и память — иначе устаревший «основной» в соседнем файле = рассинхрон, который владелец замечает.

## Развёртывание stdio MCP-сервера в Hermes (проверено 2026-08-10 на lekot/mcp-1c)

Регистрация stdio-сервера — ТОЛЬКО через официальный CLI. Прямая запись `~/AppData/Local/hermes/config.yaml` инструментами patch/write_file ЗАБЛОКИРОВАНА security-guard'ом («Refusing to write to Hermes config file»); `hermes config set` тоже не подходит для списков — пишет только скаляры (аргументы `args` строкой сломают запуск).

```bash
printf 'Y\n' | hermes mcp add <name> --command <cmd> --args "<путь к entrypoint>"
hermes config set mcp_servers.<name>.connect_timeout 60   # таймаут отдельно!
hermes mcp test <name>    # ✓ Connected + Tools discovered
hermes mcp list
```

Пифоллы (все пойманы вживую):
- **`--args` ДОЛЖЕН быть последним флагом** — всё после него уходит в argv сервера (`--connect-timeout 60` после `--args` попал в args oscript и сломал бы определение пути скрипта). Таймауты ставить отдельным `hermes config set`.
- Интерактивный промпт «Enable all N tools? [Y/n/select]» без TTY уходит в Cancelled → отвечать заранее: `printf 'Y\n' | hermes mcp add ...` (5/5 tools enabled).
- Ошибочную регистрацию чистить `hermes mcp remove <name>` и пересоздавать.
- Инструменты MCP появляются в Hermes только в НОВОЙ сессии (стандарт — как с 1c-toolkit).
- Перед регистрацией — сухой прогон сервера через `scripts/probe_stdio_mcp.py` (mcp SDK stdio: initialize + tools/list + вызов инструмента): проверить транспорт, кодировку, параметры до того, как сервер увидит Hermes.
- Развёртывать сервер в `C:\hermes\tools\<name>\` (предпочтение владельца: «не в корень клади, а куда-нибудь в тулзы»), путь без кириллицы.
- osрipt-портируемый кит (`engine/oscript-2.1.0`) уже содержит lib: opm, sql, autumn, autumn-mcp — перед «opm install» проверять `lib/<имя>`. `opm` из bash — `oscript -encoding=utf-8 lib/opm/src/cmd/opm.os ...` (без utf-8 консоль OEM-866 → кракозябры).
- **oscript-серверы резолвят пути от cwd запуска, а не от каталога скрипта** (проверено на lekot/mcp-1c): oscript НЕ кладёт путь скрипта в `АргументыКоманднойСтроки`, поэтому `Файл("main.os").ПолноеИмя` считается от ТекущийКаталог(). Hermes стартует stdio-процессы из домашней папки → справка падает: `База справки не найдена: C:/Users/<user>/src/data/...` (ручной smoke-тест из каталога сервера это маскирует!). Фикс — явный env в конфиге сервера: `hermes config set mcp_servers.<name>.env.<VAR> "<abs path>"` (`config set` умеет вложенные dict-ключи; списки — нет). Действует только в НОВОЙ сессии (переоткрыть Hermes — договорённость с владельцем).
- **Побочный эффект cwd-бага**: сервер пишет файл-указатель (`shcntx_help_db_path.txt`) в cwd процесса — `hermes mcp test` из каталога репо/кита насорит в него: в скриптах `rm -f "$(pwd)/shcntx_help_db_path.txt"`, в gitignore — запись.
- **Канонический повторный развёрт — установщик кита** `install/install-mcp1c.sh` (скачивание → распаковка в `tools/<name>` → `hermes mcp add` с `--args` последним + `printf 'Y\n'` → env-фикс → `hermes mcp test` → чистка мусора; `--force` — переустановка). Если установщик уже существует — не развёртывать вручную.
- **Ad-hoc верификация установщика**: временный скрипт в `%TEMP%` (`hermes-verify-*`), прогон, удаление. Питфоллы: (1) не грепать вывод установщика по тексту, который он не печатает наружу — `grep -q` глушит дочерний вывод, проверять его собственную сводку («...в порядке»); (2) чек side-effect'а ставить ДО собственных вызовов, которые его пересоздают (прямой `hermes mcp test` после установщика заново пишет txt-мусор → ложный FAIL); (3) в конце чистить свои артефакты.

## Verification

- После сборки проверить: сумма по категориям = итог; отсутствие выбранных DROP-имён в MD; секции не пустые.
- «Топ-3» по звёздам в каждой категории — быстрая сверка глазом.
- Для топ-репо по желанию сверить лицензию/дату с GitHub API.
